# 原生计时器模型

NativeModel读取GIL中的Start_Timer(79)、Pause_Timer(80)、Resume_Timer(81)、Stop_Timer(82)及When_Timer_Is_Triggered(83)，通过场景schema 2的tick步骤推进。事件只交给目标实体挂载的图实例；未挂载图不凭空获得事件。配置实际图使用现有Graph Code编译与挂载流程，场景可显式提供instances。

```json
{"op":"tick","dt":0.5}
```

场景server可声明required_timers，例如`[{"entity":42,"name":"neutral","minimum_events":2}]`。身份不得重复，最低次数须为正整数。联合报告逐项统计timer_events；若某项未达到最低次数，即使Lua断言通过，acceptance仍为not_checked并列出缺口，produce的必需模拟阶段拒绝验收。该合同要求计时器实际触发，不等价于每个监听图或全部业务分支都执行；必需图继续通过graph_ids约束。

原生节点参数沿用包内定义：启动为目标实体、名称、是否循环、浮点时间序列；暂停/恢复/终止为目标实体、名称。模型拒绝未知额外GUID语义的非零输入。序列不排序修复，要求1..100项、有限非负时间、相邻至少0.03秒且最后一项大于0；每实体最多100个计时器。未通过校验不替换现有计时器。

运行规则：实体与名称共同标识，同名启动替换该实体原计时器；暂停保存到下一事件的剩余时间，恢复继续，终止清除。不存在的名称操作不创建计时器。单次tick限制0..3600秒与10000个事件。事件回调可终止、暂停或替换计时器，不遗留旧序列回调。模型使用到期时间和创建序号稳定排序；序列序号从1开始、循环次数从0开始，与包内app/runtime/engine/game_state.py参考运行器一致。这些确定性调度约定不声明宿主同帧顺序一致。

联合模拟按下一条网络消息、原生计时器事件或本次tick终点拆分推进。timer_events和传输journal共用场景时钟，包含显式clock.start；延迟请求到达时才执行启动，回复传输延迟从事件发生时计算。同刻顺序约定为客户端tick、原生计时器、FIFO传输；回调新建当前时刻计时器继续处理，单个联合tick最多10000个边界。场景明确约定的排序不等于宿主同帧执行顺序。

客户端tick接收各边界间隔，不主动提取客户端内部Tween/任务的到期时间，未实现完整宿主帧调度。暂停时钟仅属于该计时器，未实现完整宿主暂停、实体销毁或持久化生命周期。

依据为references/official/概念介绍/定时器__mhufb90zbnts.md、包内plugins/nodes/server对应五个节点签名及node_data/index.json。序列事件、循环和暂停恢复来自官方文档，编号和同帧排序作为明确模型约定。完整平台计时器UI绑定、全局计时器及隐藏引擎行为不在此模型范围。

test_native_timers覆盖两套时间序列、同名不同实体、暂停恢复、替换、循环、终止及非法序列；两套序列化GIL通过实际节点触发事件，再由独立Lua客户端收到Reply并断言。该证据是受限原生图和Lua联合模型，不是本批重新编译Graph Code、编辑器导入或实机计时验收。

联合时钟专项额外覆盖非零起点、请求/回复各自延迟、事件与消息的实际发生时间，以及一次大tick和十次小tick的消息顺序/内容一致。此等价性只适用于测试的计时器与信号场景，不宣称所有依赖帧长的客户端逻辑都与步长无关。
