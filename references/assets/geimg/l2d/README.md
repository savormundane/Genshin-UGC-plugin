# 知识库：从 GEIMG 图元数据集到 Live2D 式 Lua

一套**可复现的流水线**：把一张 Live2D 风格的图集，变成游戏内用纯 Lua 驱动、能呼吸/眨眼/跟随视点/做动作的角色。

> **先把定位说清楚**：这份知识库讲的是**我们跑过的一遍**，不是要求你照搬的教程。
> 里面是两层内容，读的时候分清：
>
> - **工具用法（要遵守）**：GEIMG 怎么用 —— `02` 的三个开关约定与参数口径、
>   `03` 的数据格式与坐标系、`07` 的 API 事实与"未验证"清单。
>   这部分是"这样才对 / 这样会报错"，与画风和实现选型无关。
> - **我们的实现（案例，可以不同）**：素材怎么拆、动画怎么写、UI 怎么搭 ——
>   `01` / `04` / `05` / `06` / `08` ~ `11`。这些**只是我们的一种做法**：
>   只要你的交付效果达标，随便换。每篇末尾都分了两栏，「规则 / 不变量」是判据，
>   「参考实现（可以不同）」是我们当时的选择。
>
> 想让图元数据集去干别的事（静态展示、别的动画方案、别的引擎/平台）也没问题 ——
> 工具只负责"把图拟合成图元"，下游是你的地盘；本知识库的运行时部分（`04`~`11`）
> 是拿"千星沙箱 + Lua"当**例子**写的，不是唯一出路。

写给两种读者：

- **人**：想搞懂每一步在干什么、为什么这么干、哪些坑已经踩过。
- **AI**：想照着做一遍、或改造其中一环。每个文件末尾都有「规则 / 不变量」小节，那是硬约束；
  标了 `⚠️ 未验证` 的地方不要当成事实往下推。
  **参数上没有被禁止的项**：看到"我们没调过/差异不大"时，那是我们的观测，
  你可以按 `02` 的 2.9 自己量一次再决定。

## 这条流水线长什么样

```
图集 PNG (1024×512)
   │  ① 拆分：在 PS 之类工具里**手工扣**成同尺寸分层（自动拆分效果不好，见 01）
   ▼
parts/part_NNNN_名字.png  ×26   （411×600，二值 alpha，已摆好位置）
   │  ② 拟合：逐部件调 GEIMG，用圆/椭圆/线逼近
   ▼
fit_10k/part_*/shapes.json    （space = source_image_pixels）
   │  ③ 边缘处理：剔溢出 / 缩回轮廓 / 轮廓改色        ← 直接在数据上做，不改原文件
   ▼
   │  ④ 构建：拼数据 + 生成部件表 + 骨骼参数 + 动画代码
   ▼
l2d_anim*.lua      （自包含：数据 + 实例化 + 动画）
l2d_theater*.lua   （同上 + UI：背景/按钮/文字/拖动条/快捷键）
l2d_preview*.html  （浏览器里预览同一套数据与公式，用于调参和验收）
```

**为什么用图元而不是直接贴图**：一张整身贴图动不了；拆成图元后每个图元是一个可独立变换的控件，
就能做形变。代价是控件数量大（本项目 9941 个），所以整条链路的性能约束都围绕"每帧写多少次属性"。

## 先读这一段：两种要求，别混

这份知识库讲的是**一套跑通过的实现**，但**不要求你做得和我们一模一样**。
要求分两类：

### ① 不变量（必须满足，违反了必然出错）

这些和风格无关，纯粹是对错：

- 跨坐标系必须显式转换（画布左下原点 ↔ 控件中心原点）
- 逐帧回调必须脚本自己打开
- 数据里**半径 ≠ 直径**、**弧度 ≠ 角度**、**0-based ≠ 1-based**，不能混
- 父子/层序关系必须明确（谁盖谁）
- 每帧写入量必须与图元数量级匹配，否则卡顿

### ② 参考实现（我们的选择，**可以不同**）

**只要最终效果达标，随便换。** 例如：

| 我们这么做 | 你可以 |
|---|---|
| 26 个部件、编号 `0000`~`0026`、数字小的在上 | 任意部件数、任意命名与层序规则，**只要绘制顺序有明确定义** |
| 画布 411×600、缩放 1.05、偏移 584/135 | 任意展示尺寸；只要换算自洽（见 `03` 的公式） |
| 拟合预算 1700/1250/780… | 按你自己的边际收益曲线定 |
| 边缘阈值 0.12 / 2% / 半径 2 | 只要"外溢下降且内部不变差" |
| 骨骼锚点自动推、`bodyAmp=6`、`headKeep=0.25` | 任意幅度与曲线，只要满足验收表里的"脚钉住 / 梯度单调" |
| 跳跃参数 64/24/10/12/3.5 | 纯观感参数，按你的角色重调 |
| 具体 prefab ID、具体工具脚本 | 你自己的场景 ID 与工具链 |

**判断标准是下面这张表，不是"数字对不对得上"。**

## 验收表：要保证的就是这些效果

做完之后逐项量一遍。右列是本项目的实测值，**当参考量级看，不是及格线**。

| 要保证的效果 | 怎么量 | 参考量级（本项目） |
|---|---|---|
| **轮廓对得上** | 轮廓覆盖 / 轮廓不符像素 | 覆盖 > 98%、不符 < 2%（本 99.40% / 0.88%） |
| **边缘是硬的** | 半透明像素数 | 远低于软边（本硬边 ≈1136，源图 0） |
| **没有白描边** | 最外环「明显偏亮(>25)」像素 | 修完应大幅下降（本 1568 → 82） |
| **没伤到内部** | 内部 RMSE（离轮廓 >3px） | **不因边缘处理而变差**（本 22.40 → 22.23） |
| **位置正确** | 图元坐标范围 | 不超出半画布（本越界 0 个） |
| **脚钉住** | 脚部图元的水平位移 | ≈ 0（本 0.00px） |
| **越往上动越多** | 躯干/头位移梯度 | 单调递增、无台阶（本 0.66 → 17.29px） |
| **眨眼读得出** | 眼内容压缩数 + alpha 变化数 + 能否还原 | 三者都要有且能还原（本 681/681/681） |
| **动作互不干扰** | 逐动作位移量测 | 每个动作都有非零位移，互不抵消 |
| **不卡** | 每帧 API 写入次数 | 明显低于全量（本 596k/秒 → 197k/秒；**补间化呼吸后可到 ≈0**） |
| **不静默失败** | 日志 | 关键步骤都有日志（容器/UI/按键/铺完/层序） |

这些都能在**不进游戏**的情况下量（`attachments/l2d_verify_*.py`、`attachments/l2d_edge_probe.py`）。
真机只需确认那几件预览测不出来的事（见 `07` 的未验证表）。

## 五分钟速览（只记这几条也能跑通）

1. **先定三个开关**（`02` 的 2.0）：要保住图片的边缘形状就开**边缘感知**（与是否 PNG 无关；
   带透明通道的图 **必须**开）；**黑白交替底色**是用来拟合黑色/深色内容的，**建议常开**；
   像整体环境图这种不关心边缘形状的，两个都关掉、走标准拟合，**更省图元**。
2. **图元总数按"同一时间、同屏"算**，经验量级是同屏 **3000 以内** —— 这是**建议，不是规矩**，
   多少由你按用途和机器判断（`02` 的 2.8）；自己这台机器上跑一次 benchmark（2.9），
   比抄我们的耗时数字可靠。
3. **拆分层的 alpha 最好二值（0/255）** —— 非二值不是不能做，但"硬边"这一整套判断就不成立，
   而且后面（`06`）的白描边问题会更容易发生。
2. 每个部件的**绘制顺序要有明确定义**。我们用"文件名编号小的在上"。
3. 拟合产物 `shapes.json` 的坐标空间要**统一**（我们用 `source_image_pixels`）；
   放大拟合过的要除回去。
4. 一个图元 = **一个图片控件**：圆形贴图 + `ImageType.Stretch` + `imageColor` + 尺寸 + 旋转。
5. 控件位置用「**画布中心原点**」，`GetCursorUIPos` 用「**画布左下角原点**」，
   两者差半个画布——漏减就会整体窜到右上角（本项目实际踩过）。
6. **没有 `alpha` / `zIndex` 字段**：透明度改 `imageColor`，层序用 `SetSiblingIndex`。
7. 逐帧回调**默认是关的**，脚本必须自己 `script:EnableUpdate(true)`。
8. 图元上万时**别每帧全写**：降频 + 位移小于阈值不写 + 视点没变就跳过骨骼场。
   动作要用**连续位移场**，别给相邻部件不同权重（后者必然在边界撕开）。

## 名词表

| 词 | 含义 |
|---|---|
| **图元 / shape** | 一个圆、椭圆或线段，用位置+尺寸+旋转+颜色描述一块色块 |
| **部件 / part** | 一个图层（如"前发""左腿"），由几十到上千个图元组成，部件内图元按顺序叠加 |
| **GEIMG / GEIMG 工具 / GE 图片工具** | 把 PNG 拟合成一堆图元的工具（基座是 LPGS 拟合算法）。**可执行文件不随本包发布**，脚本通过它的命令行调用 |
| **源图像素空间** | 手扣图层的坐标系：411×600，原点左上，Y 向下 |
| **画布空间** | 游戏 UI 坐标系：原点左下，Y 向上（尺寸由 `game.GetUICanvasSize()` 给） |
| **控件空间 / anchoredPosition** | 控件位置用的坐标系：原点在**容器中心**，Y 向上 |
| **骨骼位移场** | 位移 = (x,y) 的连续函数，替代"按部件给权重" |
| **硬边** | 边缘只有全不透明/全透明两种状态（与二值 alpha 对应） |

## 这些结论是从哪来的（可信度分级）

| 来源 | 能信到什么程度 |
|---|---|
| **实机运行** | 最高。踩坑清单里有一半是只有真机才发现的（忘开逐帧回调、容器就绪时序、回调签名） |
| **真 Lua 运行时实跑**（lupa + luaparser） | 高。运动/负载/按键这些数字都是这么量出来的；**但不含引擎真实开销**（用的是桩函数） |
| **可用实例的 API 类型定义**（EmmyLua stub） | 高。字段名、类型、签名、枚举以它为准 |
| **从官方 PDF 整理的接口表** | 中。**字段名/类型可信，解释列不可全信**（PDF 里的表格被裁过，有些说明是后补的） |
| **我们的推理与取舍** | 看标记：`【实测】`/`【约定】`/`【可调】`；标 `⚠️ 未验证` 的一律别当事实 |

**读的时候注意**：本项目早期还写过一份计划书（在实机验证之前），里面有几处结论后来被实测推翻
（例如当时不确定坐标系、API 名称写的是旧的 `EnableTick`）。
**如果看到和本知识库冲突的说法，以本知识库和 `07-API速查` 为准。**

## 本知识库的证据等级

每处结论都标了来源，看到这些标记请按对应可信度使用：

- **【实测】** 在真 Lua 运行时（lupa）里跑出来的数字，或真机反馈
- **【约定】** 我们定下的规则（例如"编号小的在上"）——**换一套同样可行，只要保持一致**
- **【可调】** 具体数值，按你的素材/手感调；判定看效果不看数字
- **⚠️ 未验证** 推论或文档说法，尚未在真机确认
