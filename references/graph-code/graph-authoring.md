# 节点逻辑设计与实际连接

先按[平台接口与工程合同](../workflows/implementation-policy.md)区分自定义接口和已有定义。

## 从行为到图

为每个功能明确触发事件、权威实体、可读状态、条件、写入、反馈和下一状态。用状态机组织初始化、运行、暂停或取消、结算和重开。每个事件应有可追踪的执行入口。将查询值的数据线接到实际读取它的端口，并单独连接执行线。

明确条件成立和不成立时的路径。为循环设定终止条件和每帧或每次事件的预算。区分局部、图、实体、全局与持久变量，为重开、换局、重连和离场分别定义重置规则。使用定时器时，核对实际接口和时间源，处理重复启动、迟到的事件和访问已销毁对象的情况。

涉及跨端通信时，先由 Agent 设计协议表或读取已有表，明确名称、方向、目标、字段类型与顺序、会话或回合标识，以及去重和失败处理。单人关卡中的原生节点与 Lua 也应明确发送与响应规则。只在玩法需要多人系统时引入房间。

## 节点与类型

查阅包内节点库和官方资料，选择事件、分支、循环、计算、变量和动作节点，并核对图作用域和具体签名。Graph Code 是一门受限的领域专用语言，应在支持范围内编写完整逻辑并执行严格编译。编译失败时，先修正声明、参数或类型，并保留用户要求的节点图行为。

同类节点的具体泛型、结构体绑定、输入输出类型、变参数量和引脚索引必须一致。自定义信号及结构体相关定义共同扫描编号，核对各通信角色的声明、实例和注册关系。不能只验证连线目标节点存在。

插件维护的值端口合同见 [node-contracts.json](../../scripts/node-contracts.json)。查询和源码检查会核对登记的原文章节及端口。首个合同是 7.1 的「创建实体」，用于确认值输入，并在 Graph Code 中拒绝把它当作值读取。流程端口来自随包编译器定义，原生格式与宿主支持另行验证。添加或调整合同时先从对应版本取证，再运行合法编译和拒绝用例。

## 选择文件路径

- 新图：显式编写Graph Code、项目资源与build.json，严格构建，回读事件、执行/数据连接、类型、常量及变量。
- 既有图修改：按当前样本定位唯一锚点，验证修改前提，生成最小补丁；不为复用新增图命令覆盖原图。
- 当前编译器不支持的结构：依据真实节点/声明编写当前项目适配，保留原结构和未改字段，独立检查输出。缺少可验证结构时才请求最小样本。
- 实体、模板或挂载缺失：有可核验模型时创建并写入引用，分配唯一标识；核对图作用域、宿主类型、入口生命周期和实例依赖，再回读绑定。

构建配置的格式见 [节点图构建](node-graph-workflow.md)。任务需要挂载时，Agent 应按有样本依据的流程完成挂载，并遵守现有脚本的文件保护规则。

## 有意义的验证

优先验证从实际事件、条件、写入到响应或画面反馈的完整路径，并覆盖取消、超时、重复、旧包和重开。校验器应能独立发现生成结果中的错误，保留已发现的声明或索引错误作为失败用例。整合后核对内嵌 Lua、图集合、信号、变量、挂载和源摘要。

回读用于确认产物包含所需结构，逻辑模拟只覆盖模型中的行为。编辑器导入和平台实际行为需分别验证。无法操作宿主时，继续完成已授权的其他工作，并交付可供复测的文件。
