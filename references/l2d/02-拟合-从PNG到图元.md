# 02 · 拟合：从 PNG 到图元集合

把每个部件（PNG 图层）拟合成一堆圆/椭圆/线段。工具是 `GEIMG 工具`。
这一步的产物决定了后面"像不像"，也决定了控件数量（= 性能成本）。

---

## 2.0 先定三个开关（工具口径，与提示词同步）

数值参数（预算、放大倍数、阈值）怎么调是后话。这三个开关决定"图元花得值不值"，
先按**这次要的效果**定，再看图微调：

| 这次要的效果 | `fit mode` | `edge-aware`（边缘感知） | `alternate-bg`（黑白交替底色） |
|---|---|---|---|
| **要保住图片的边缘形状**（角色/图标/任何要抠到别的背景上的图，**不管是不是 PNG、有没有透明通道**） | 有透明通道 → `transparent`；**不透明但要让图元不鼓出画面/轮廓 → 也用 `transparent`**（实测：标准模式的圆形会越出原图边界，透明底模式不会） | **开** | **建议开** |
| **不关心边缘形状**（整体环境图、背景图、整幅都要的内容） | `standard` | 不开（同一片区域用更少图元就够，**图元性价比更高**） | 看内容里有没有黑色，见下 |

- **`edge-aware`（边缘感知）**：拦的是"图元跨出内容边界、鼓到轮廓外"。
  **只要这一次交付要保住边缘形状，就开它，与是否 PNG 无关**；
  本知识库的场景（lua + 带透明通道的 PNG）**是必须开的**。
  它的代价是候选尺寸被边界限制、同样图元数下内部可能更糊——所以"不要边缘形状"的图
  干脆别开，把预算全花在内容上。
  ⚠️ 未验证：它在 `standard` 模式下是否也起作用（`fit recommend` 说"标准拟合模式下它不适用"，
  但引擎实现里开了它会给画布加一圈内衬、否决贴边候选）。**要保边就用 `transparent` + 开它**，这条有实测。
- **`alternate-bg`（黑白交替底色）**：它专治**黑色/深色内容**。
  透明底模式下画布底是黑的，纯黑内容和底色没有差别、误差为 0，**一个图元都拟不出来**。
  所以**建议常开**，除非确认这张图里没有黑色部分。代价是它会周期性全量重放历史图元，
  大图/高 `max-dim` 下会明显变慢——**这是"量一量再决定"的开关，不是"永远别开"**，
  量法见 2.9。切换间隔：`alternate-interval` 默认 30（20~50 之间，越小越慢）。
  ⚠️ 已知边界：**内容接近纯黑（RGB 接近 0）时它只能救一半**——深色底那一拍仍然看不见
  （实测：297×140 近纯黑细条的透明图，透明底模式 0 个图元；开交替底色后能出图，但深底那一拍仍是 0）。
  这种情况最稳的是让内容不是纯黑（加描边/反相）。

> 这两个开关的口径与工具手册（`docs/GEIMG_AI上手提示词.md` 第三节）一致；
> 2.2 起的数值是**本项目这一次跑下来的取值**（一台机器、一批素材，当参考量级看），
> 换素材要按 2.3 的判断方法（预算按边际收益）和 2.9 的 benchmark（耗时自己量）重新定。

## 2.1 为什么是"图元"而不是直接贴图

一张整身贴图**动不了**——你没有像素级的变形能力。拟合成一群几何图元后：

- 每个图元 = 一个可独立设置位置/尺寸/旋转/颜色的控件
- 于是可以做**形变**（头转过去时五官按柱面分布位移，而不是整层平移）
- 代价：控件数量大（本项目 10030 个），所以整条链路都在跟"每帧写多少次属性"较劲

另一个好处：图元是**矢量描述**，放大不会糊（但会暴露图元是圆拼的，见 06）。

## 2.2 关键参数（本项目实际用的值）

命令行的调用方式见 `attachments/l2d_superfit.py` 与
`attachments/l2d_fit_batch.py`。参数含义：

| 参数 | 本项目取值 | 含义与经验 |
|---|---|---|
| `fit mode` | `transparent` | 有透明通道的图用这个模式（见 2.0） |
| `alpha-threshold` | `64` | **低于这个 alpha 当背景**（工具默认 128）。我们调低是为了让抗锯齿软边也算内容，零件交界处才不留缝；40~100 之间试 |
| `max-dim` | `600 × 放大倍数` | 拟合画布上限，放大 3 倍时写 1800。判据是"最细特征在拟合分辨率下留 2~3px"；工具的 `fit recommend` 会按边缘密度给 600/800/1000/1200，两者等价，按自己的素材定 |
| `candidates` | `64` | 每次尝试的候选图元数，越大越慢越准（工具默认 64） |
| `speed` | `5` | 引擎内部的速度档（工具默认 5） |
| `reserve-ratio` | `50` | 【可调】一半预算留给"精度阶段"（小图元）。我们观察到发丝分股更好；工具手册里另一组误差口径的对照认为差异在重复跑波动内。**这是取舍不是定论**：先按默认跑，嫌发丝糊再 30~50 之间试 |
| `edge-aware` | `on` | 要保边就开（见 2.0） |
| `alternate-bg` | `on`，间隔 `30` | 拟合**黑色/深色内容**用，建议常开（见 2.0） |
| `fit shapes N` | 见 2.3 / 2.8 | 总预算（图元数）。**同一时间、同屏**的总数建议 3000 以内，具体由你判断（见 2.8） |

### ⚠️ 一个待复现的观察：edge-aware 与勾线

我们的记录里有两条互相冲突的信息，现在按"要保边就开"处理（见 2.0），但值得自己复现一次：

- 一部分日志（`manifest.json` / `session.json`，引擎实际写下的）记的是 `edge_aware: true`；
- 而汇总文件 `_summary.json` 里记的是 `false`，附注说：**开着时会否决所有跨内容边界的候选，
  而勾线恰在边界最外 1~2px，可能导致边缘画不出来**。

**遇到"勾线断了/边缘画不出来"时按这个假设排查**（关掉边缘感知对照跑一次），
常规情况仍按 2.0 开——不开的代价是图元溢出剪影。⚠️ 未验证。

## 2.3 预算怎么分：按边际收益，不平均分

我们这一轮观察到的规律：

> **小部件饱和得快：预算给过饱和点之后，再加基本只花时间。**

最夸张的一例（在我们的机器上）：`mouth` 给 120 个图元跑了 **1505 秒**，给 45 个只要 **3.7 秒**，
而**质量没有差别**。耗时的绝对值会随机器变化，但"过了拐点再给就没收益"这个形状是可复现的。

本项目的分配（10k 版，共 10030 图元）：

| 部件 | 预算 | 理由 |
|---|---|---|
| 前发 | 1700 | 成品里最大可见面积，到 v5 的 560 还在变好 |
| 衣服 | 1250 | 层叠 + 金边，420 之后仍在变好 |
| 头发花装饰 | 780 | 第二大可见面积，线条密集 |
| 腿（左右） | 780 / 700 | 到 260 仍在变好（宝石、V 形带） |
| 脸 | 480 | 大片平滑皮肤，实测 100/200/320 **无差别** → 给到下限即可 |
| 眼白 | 60 / 50 | 强边缘像素为 0（纯平滑渐变）→ 给最小底 |
| 嘴 | 60 | 45 即饱和 |
| 被完全盖住的裤子 | 40 | 平时露出 0px，但动画会露，不能给 0 |

**判断方法**：拿一个部件跑 3~4 个预算档，肉眼比"哪一档开始看不出差别"，取拐点。

## 2.4 细结构：放大拟合（×3）

**原因不是"更精细"，而是图元尺寸有绝对下限**：

```
圆的半径下限 ≈ max(2, …)      线段的 Ry 下限 = max(1, …)
```

在 411×600 上，这些下限**比勾线本身还宽** —— 1~2px 的线根本表达不出来，
拟合器只能用一个大得多的圆去近似，线就糊了。

做法：把部件图 **Lanczos 放大 3 倍** 再喂给引擎，导出后把坐标/半径**除回 3**。
这样 1~2px 的线在拟合分辨率下有 3~6px，能表达出来了。

哪些部件要放大（本项目）：**细线类全部 ×3**（眉毛、睫毛、眼线、五官、勾线、飘带、腿、手臂……），
大片平涂 ×1（眼白、脸、后布、后发、裤子——放大对它们只是白花时间）。

### 要点：透明区会被卷进边缘（不管你怎么放大）

**根因与做法无关**：原图透明区的 RGB 是**纯白**，而 **PIL 的 `resize` 对 RGBA 四个通道
各自独立插值，不做预乘 alpha**。于是白色被卷进轮廓最外 1~3px 的半透明像素，
**拟合器照着这些偏亮像素取样，成品轮廓外侧就多出一圈浅色**。

这是本项目"边沿几个像素的白色描边"的根因（完整因果链见 `06-边缘与画质.md`）。

推荐做法（也是我们用的）：**放大前先把透明区的 RGB 染成邻居的颜色**
（`upscale_edge_aware()`，在 `attachments/l2d_fit_batch.py`）。

**反直觉的实测结论**：用"预乘 alpha → 插值 → 反预乘"**反而更糟** ——
Lanczos 的负瓣过冲会被 `1/alpha` 放大，最外圈 RGB 从 (248.6,244.7,242.1) 变成纯白 (255,255,255)。

**如果你不放大了**（例如图元尺寸够、线够粗）：这一步可以跳过。
但**透明区颜色仍然是"以后会出问题的地方"** —— 只要有任何一步做插值/缩放，
它就会卷进来。实在不想管，就在边缘处理阶段（`06`）收尾。

## 2.5 导出产物

每个部件一个数据集目录，关键文件：

```
<数据集>/part_0001_前发/
    shapes.json        ← 图元（下游只用这个）
    manifest.json      ← 引擎写下的实际配置 + 预处理信息（以它为准）
    preview.png        ← 用图元重绘的预览（RGBA，可叠加）
    preview_on_white.png
    shapes.csv
    lua/geimg_render.lua
```

**导出的坐标空间要统一，并在数据里写明**（我们用 `source_image_pixels`）：
放大拟合的要把 x/y/r/rx/ry 全除以倍数，并把 `space` 字段写成换算后的空间名。
本项目专门有 `rescale_dataset()` 做这件事
（它同时会把 `preview.png` 用换算后的图元**重绘**一遍——引擎给的原 preview 是放大空间的，
留着它就是"看着对、其实错位"）。

⚠️ 这是本项目踩过的坑：26 个部件里 6 个在源空间、20 个在放大空间，装配时必然对不上。

## 2.6 规则分成两栏

### 必须满足（不满足就坏）

- **每个部件的坐标空间要统一，并且声明清楚。**
  我们统一到 `source_image_pixels`（源图像素）；换别的空间也行，
  但所有部件必须同一个，且下游知道怎么换算到屏幕。
- **图元数组顺序 = 绘制顺序**（这是 GEIMG 输出的约定：下标 0 在最底层）。
  如果你的数据格式没有隐含顺序，就**额外记一份顺序**。
- **半径/直径、弧度/角度不能混**（见 `03`）。
- 放大拟合过的部件，**坐标必须除回同一个空间**——否则装配时必然错位。

### 参考实现（可以不同）

| 我们的做法 | 可以这样 |
|---|---|
| 统一到 `source_image_pixels`，`space` 字段写明 | 用缩放后的空间、或归一化坐标（0~1），只要统一 + 能换算 |
| 细线部件 ×3 放大 | 加大 `max-dim` 让引擎内部提高分辨率；或接受细线表达不出来（画风允许就不必） |
| 预算 1700/1250/780… | 按你自己的边际收益曲线定（方法见 2.3） |
| `reserve-ratio = 50` | 30~60 之间试；越高越偏向小图元精度 |
| `alpha-threshold = 64` | 40~100 之间试；太高会让零件交界处留缝 |
| 边缘处理在构建脚本里做、不改 `shapes.json` | 直接改也行，但要留一份原始备份（否则没法回滚重调） |

### 怎么判断拟合够用了

不要跟我们的数字比，问这三个问题：

| 要保证 | 怎么量 |
|---|---|
| 细线画得出来 | 把 `preview.png` 和原图叠起来看勾线/睫毛有没有断、有没有变粗成块 |
| 颜色没跑偏 | `preview` 与原图的颜色误差（RMSE 量级 20~40 属正常） |
| 预算没白花 | 同一个部件跑两档预算，**看不出差别**就说明早饱和了，往下调 |

## 2.7 常见错误

| 现象 | 原因 |
|---|---|
| 细线（勾线、睫毛）画不出来 | 没放大拟合，图元尺寸下限比线还宽 |
| 轮廓外一圈浅色 | 透明区是纯白 + 非预乘放大（见 2.4） |
| 装配错位 | 各部件坐标空间不一致（有的除了倍数、有的没除） |
| 五官糊成一团 | 预算给太少；或 `reserve-ratio` 太低，精度阶段没预算 |
| 小部件拟合跑了几十分钟还没提升 | 多半是预算给多了、早就饱和（见 2.3）；也可能是这台机器/这一版引擎在稀疏图上本来就慢——先按 2.9 量一次再下结论 |

## 2.8 图元总数：**同屏 3000 是经验上限，具体多少由你判断**

工具的图元数是全局预算（`fit shapes N`）。经验量级是**同一时间、同屏 3000 以内**，
但这是**建议、不是规矩**——最终多少由你按"这次交付的用途 + 用户的机器"判断：

- **按"同一时间、同屏"的总数算**，不按单张图算：三张各 2000 图元的图同屏出现就是 6000。
  这是这里唯一要守住的量级关系。
- **不关心边缘形状的图（整幅环境图/背景）可以明显低于 3000**：
  关掉 `edge-aware` 与 `alternate-bg` 走标准拟合，同一片区域用更少图元就够（见 2.0）。
- **要合成特写、要看清五官与发丝就往上加**：本项目这一版是 10k 级别（10030 个图元、
  26 个部件），它对应的代价写在 `04` 与 `10`/`11`——每帧写入、首次创建成本、以及
  一整套"每帧别全写"的省法。**上万不是不能做，但要配这套省法并且有实测支撑。**
- **别因为"我们表里写着 3000"就不敢加，也别因为"越像越好"就无脑加。**

## 2.9 在**你的**机器上量一次（benchmark）

我们文档里所有耗时数字都来自**一台机器、一批素材**；换机器换素材就该自己量一次。
**一次 2~3 分钟就够**：

```bash
# ① 拿真正要用的那张图，设成最终打算用的参数
advanced set max-dim 1000            # 就用你打算用的值
fit mode transparent                 # 或 standard，按 2.0 的结论
advanced set edge-aware on

# ② 小预算试跑，量一个点
fit shapes 200
fit start --until full --timeout 120 --json    # 看 data.elapsed_ms 与 data.shape_count

# ③ 同一配置再跑一次，取两次里较大的耗时（重复跑波动能到 40%），然后线性外推：
#      预计秒数 ≈ 实测秒数 × (目标图元数 / 实测图元数) × 1.5
```

拿到"预计秒数"之后做两件事：**① 定图元数**（能等的秒数 ÷ 单图元秒数，再和 3000 取小）；
**② 定分段**（预计超过 ~90 秒就 `--timeout 60` + `fit resume` 一段一段跑，中断不丢成果）。
