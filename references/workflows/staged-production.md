# 千星奇域阶段式制作

## 适用范围

本流程面向原神千星奇域的玩法、节点图、客户端 Lua、控件、素材、动画、多人信号、平台存档、成就及 GIA/GIL 交付。制作、续作或修复玩法时，由 `miliastra-editor` 按需调用相应 Skill。接口查询与局部修改直接进入对应 Skill，按任务选择检查。

用户不需要掌握技能名、节点连法或构建命令。Agent负责决定实现路径并调用工具。已授权任务不在每一步重复等待确认；需求足够时简要说明假设和计划后执行，只有会改变核心玩法/原有数据、或确实缺少必要输入时询问。阶段检查是产物和证据检查，不是额外审批。

## 1. 读取当前现场

读取项目当前的 README、开发约定、源码、构建入口、清单和基底。记录版本、输入摘要、用户要求保留的内容、平台配置和目标产物。明确交付的是完整关卡、单张图的 GIA、Lua 模块还是素材数据，并按需求确定单人或多人、Lua 界面或原生实体、PC 或手机。

明确当前输入、交付目标、仍缺的条件和可以继续的工作。修复任务先保留可复现的输入和操作。证据或摘要不符时，从[工程只读诊断](project-diagnosis.md#交付文件与清单不一致)找到差异来源。

## 2. 明确玩法与验收

将一句话展开为核心操作、事件、状态、胜败、重开和必要边界。可逆细节自行定合理默认，记录假设；不擅自改玩家规则或历史存档。每项需求写成能观察的验收条件，例如“重复提交不重复结算”“隐藏页不继续命中”“重开后计时正确重置”。

修复要区分当前已复现、仅用户报告、仍待原生验证；只在可复现的层级建立回归，不能把模拟复现写成宿主根因。

按 [体验制作与游玩检查](playability-workflow.md) 明确操作反馈、规则/表现分工、目标设备、输入边界和素材一致性。

## 3. 设计实现与任务顺序

由Agent选Lua、服务器/客户端Graph Code和原生资源的职责；新变量、协议和定义由Agent设计，已有合同读取兼容。列出事件入口、执行/数据线、图/实体宿主、信号参数/顺序、重置/存档及资源预算，避免多个技能各猜一套。

每个任务写清实际文件、负责能力、前置任务、产物和验证方法。先排依赖，再分小步；一个任务应能独立判断是否完成。计划保存在所属奇域项目现有制作文档或需要恢复的plan.json，不把具体玩法与进度写入AGENTS或插件通用资料。

| 工作 | 使用的现有能力 |
| --- | --- |
| 完整需求和制作顺序 | miliastra-editor |
| Graph Code语法、类型和连接 | miliastra-graph-code |
| 控件与生命周期 | [Miliastra Editor · Client Lua](../../skills/miliastra-editor/SKILL.md#client-lua) |
| 权威状态、信号与恢复 | Graph Code与Client Lua的多人流程 |
| 原生写回与字段保护 | miliastra-gil |
| 信号→图→Lua组装 | GIL组装流程 |
| 位图/参数图形与静态数据 | miliastra-assets |
| 帧/分层动作与控件池 | Client Lua动画流程 |
| 千星奇域生成目录数据合并 | 生成目录合并指南 |
| 交付来源与证据失配 | 交付诊断流程 |

## 4. 先打通最小玩法闭环

完整的新玩法先完成进入、首轮操作、规则推进、胜败和重开，接通实际事件与界面反馈，再扩展内容、成长和美术。用户要求原生节点时必须连接实际节点图，不能以空事件、打印图或客户端假结算代替。用户要求复杂原生/多人功能时，闭环仍包含所需原生执行和最小真实通信。

这不是限制只能做Lua小游戏，也不要求先造通用框架。需要专用节点/字段适配时读取真实结构后直接编写；缺少宿主依据时指出最小缺项，继续不依赖它的工作。已有成熟项目做目标增量，不为本流程重写全游戏。

## 5. 小步实施、逐项回归

按任务实现真实源码、图、资源和必要补丁；一个可验证增量完成后运行对应检查再继续。行为修复优先记录失败案例→修复→原案例通过，再查相邻状态；新功能先明确预期再测实现。纯文案/可逆小改动不强造测试。失败先定位输入、声明、状态、执行、渲染或平台环节，不连续堆补丁，也不跳过类型/保护检查。

生成Lua目录在生成期合并并校验覆盖，不手改生成物。需要随机性/存档时保持预览与实际同源、明确规则版本和迁移；未知/坏档不静默改成成功。多人操作核对来源、会话、回合、去重和断线边界。

## 6. 两轮自查

第一轮对照需求：每项行为对应实际实现、资源和验收结果，避免遗漏/越界。第二轮检查接入质量：API签名、类型、端口、声明ID、生命周期、重开清理、命中、控件/节点/存档预算和来源摘要。可按环境顺序执行，不要求另开会话或默认启动子Agent。发现问题修正并重跑受影响检查，不用“审查已完成”代替证据。

## 7. 组装与回读

按[组合制作与交付](produce.md)使用 `produce` 串联素材、协议、动画、节点图和 Lua 写入。需要项目专用路径时沿用已核验工具。按GIL组装能力处理信号与图依赖；严格编译及字段保护保留。只在真实绑定合同和实际输出匹配时确认挂载。源码、内嵌Lua、图集合、参数、模板、音乐与目标字段逐项回读。

检查最终交付文件，并在报告中核对本轮产物的摘要。交付文件另存，遵循项目的版本保留约定。

## 8. 游玩检查与交付反馈

沿进入→主操作→反馈→结果→重开检查最终文件；多人/存档再检查迟到包、恢复与发布关卡重进。按 [游玩检查](playability-workflow.md) 记录步骤、预期、实际与证据层级，区分规则、输入和表现问题；未执行项明确待验。

交付所需源码和可定位的GIA/GIL/素材文件，说明已实现行为、当前检查和仍待编辑器/实机的项。静态、逻辑模拟、编辑器和实机分别记录；仅有哈希相同不证明玩法正确，仅有变量回读不证明跨次持久化。没有宿主工具时完成源码和离线交付，并给最短复测路径，不提前停在计划。

用户反馈作为下一轮输入，绑定具体版本与现象，先复现再定位；不恢复已取消的功能，也不自动上传关卡、操作编辑器或修改已安装插件缓存。

## 阶段与证据检查命令

```text
python scripts/qianxing.py workflow guide --kind feature
python scripts/qianxing.py workflow guide --kind fix
python scripts/qianxing.py workflow check PLAN.json --report OUTPUT/production-report.json
```

kind支持feature/fix/ui/assets/delivery，各自缩减为适用阶段。check检查需求覆盖、任务依赖、实际技能、完成声明所附文件摘要，以及production-report里的产物摘要/失败状态；它不会执行计划里的命令，不把手写的editor/host证据自动认定为独立实测。普通任务无需先创建此文件才能开始，长任务需要恢复和追踪时再用。

```json
{
  "schema": 1,
  "domain": "genshin-qianxing-ugc",
  "kind": "fix",
  "goal": "修复当前奇域重开后的输入状态",
  "requirements": [{"id": "R1", "acceptance": "重开后首轮操作能正常执行"}],
  "steps": [{"id": "S1", "phase": "inspect", "owner": "miliastra-editor", "requires": [], "requirements": ["R1"], "status": "pending"}]
}
```

done步骤需要evidence列表，每项为kind（source/static/simulation/editor/host）、path和sha256；blocked步骤需要具体blocker。按 [制作流程](produce.md) 选择合适的工具。
