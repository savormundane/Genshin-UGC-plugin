# 原生计时器模型

`NativeModel` 读取 GIL 中的 `Start_Timer`（79）、`Pause_Timer`（80）、`Resume_Timer`（81）、`Stop_Timer`（82）及 `When_Timer_Is_Triggered`（83）。用 schema 2 场景中的 `tick` 推进时间。事件只投递给挂在目标实体上的图实例。使用现有 Graph Code 编译与挂载流程准备节点图，可在场景的 `instances` 中明确指定实例。

```json
{"op":"tick","dt":0.5}
```

场景server可声明required_timers，例如`[{"entity":42,"name":"neutral","minimum_events":2}]`。身份不得重复，最低次数须为正整数。联合报告逐项统计timer_events；若某项未达到最低次数，即使Lua断言通过，acceptance仍为not_checked并列出缺口，produce的必需模拟阶段拒绝验收。该合同要求计时器实际触发，不等价于每个监听图或全部业务分支都执行；必需图继续通过graph_ids约束。

启动参数为目标实体、名称、是否循环、浮点时间序列。暂停、恢复和终止使用目标实体与名称。部分原始 GIL 的启动节点还连接当前事件的所属实体 GUID。模型只有在目标就是当前图实例的所属实体，连线指向当前事件的 GUID 出口，且场景提供了对应 `server.entity_guids` 时才接受这条连线。序列要求 1 至 100 项、有限非负时间、相邻至少 0.03 秒且最后一项大于 0。每实体最多 100 个计时器，无效序列保留现有计时器。

按实体和名称标识计时器。同名启动替换该实体的旧计时器。暂停时保存下次触发的剩余时间，恢复后继续计时。终止时清除计时器。模型按到期时间和创建序号排序，每个 `tick` 限 0 至 3600 秒和 10,000 个事件。循环次数从 0 开始，序列序号默认从 1 开始，与随包参考运行器一致。原始图按 `0`、`1` 匹配事件序号时，可显式设 `server.timer_index_base: 0`。

联合模拟按下一条网络消息、原生计时器事件或本次tick终点拆分推进。timer_events和传输journal共用场景时钟，包含显式clock.start；延迟请求到达时才执行启动，回复传输延迟从事件发生时计算。同刻顺序约定为客户端tick、原生计时器、FIFO传输；回调新建当前时刻计时器继续处理，单个联合tick最多10000个边界。场景明确约定的排序不等于宿主同帧执行顺序。

客户端tick接收各边界间隔，不主动提取客户端内部Tween/任务的到期时间，未实现完整宿主帧调度。暂停时钟仅属于该计时器，未实现完整宿主暂停、实体销毁或持久化生命周期。

序列事件、循环、暂停和恢复依据官方资料与包内 `plugins/nodes/server` 的五个对应节点签名及 `node_data/index.json`。模型另行定义编号和同一帧内的处理顺序。完整平台计时器 UI 绑定、全局计时器及隐藏引擎行为不在此模型范围。 [官方《定时器》](https://act.mihoyo.com/ys/ugc/tutorial/detail/mhufb90zbnts)

模型检查可覆盖同名不同实体、暂停恢复、替换、循环、终止及非法序列。在带信号的场景中核对请求到达、事件触发与回复的各自时间，并比较单次与分段 `tick`。真实计时与同帧顺序通过对应发布关卡验证。 [验证等级](validation.md)
